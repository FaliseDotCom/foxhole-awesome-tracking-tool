# Plan: war log

Date: 7 October 2026. Status: v1 done (`lib/warlog-diff.js`, `stores/warlog.js`,
`components/warlog.svelte`, `assets/css/warlog.css`); v2 built (`.api/lib/warlog*.php`,
`.api/cron/record.php`, `/api/log`, server source and fallback in `stores/warlog.js`); the
DirectAdmin cron job still has to be set up. Not built from the plan: the JSON-lines storage
fallback (without `pdo_sqlite` the log API answers 503 and browsers use their own comparison),
and ETag requests (the recorder reuses the data `/api/data` already fetched).

A panel on the left that lists what changes in the war while the page is open: towns captured
or lost, structures built or destroyed, towns scorched, the victory town count moving. Each
entry is clickable and moves the map to where it happened.

- **v1 (done)** runs entirely in the browser and keeps nothing: every visitor compares the map
  data every 10 seconds, the log starts empty when the page opens and is gone on reload.
- **v2 (next)** moves the work to the server: the server detects the changes, keeps them, and
  the browser only fetches the log. Everyone sees the same history, it is filled as soon as
  the page opens, and it includes what happened while nobody was watching. The browser's own
  comparison from v1 stays as a fallback for when the server log is not responding.

## What the data allows

The world store already receives the full map every 10 seconds (`/api/data/<shard>`). Per hex
it has a `v` (version, changes when anything in the hex changes), `l` (last update time in
ms), `s` (scorched victory towns), and the items `{ x, y, t, i, f }` (position, team, icon
type, flags). Comparing a hex's new items with the previous ones gives every change:

| Change | How to detect | Example text |
| --- | --- | --- |
| Captured | same position and type, team `''` → `W`/`C` | **Wardens** took Town Base Tier 2 – The Spine |
| Lost | team `W`/`C` → `''` | **Colonials** lost Relic Base – Brine Glen |
| Upgraded | same position, type changes (Town Base Tier 1 → 2, relic tiers) | Town Base Tier 1 → Tier 2 – Iron's End (Wardens) |
| Scorched | flag `0x10` set | Victory town scorched – The Salt Farms |
| Town claimed | flag `0x20` set or cleared | Town claimed – Abandoned Ward (Wardens) |
| Built | new position | **Colonials** built Seaport – Tine |
| Destroyed | position gone | Mortar House destroyed – The Pits (Wardens) |
| Construction | build site flag `0x04` set as the team appears, or a new position that is a build site | **Colonials** started building Mortar House – Clahstra |
| Completed | build site flag cleared, team kept | **Colonials** finished building Mortar House – Clahstra |
| Abandoned | build site flag cleared as the team goes | not logged: sites are placed and cleared over and over |

A build site takes the team of whoever builds it, so without the flag a started site reads as a
capture and a cleared one as a loss. Construction at a spot that started within the last 30
minutes is not logged again (`REPEAT_WINDOW` in the recorder, `repeat_window` in the store).
| Victory towns | totals from the war store change | Wardens now hold 25 of 34 victory towns |
| War ended | `winner` in `/api/war` changes | **Wardens** won war 141 |

Items have no id, so they are matched by position: the API proxy rounds coordinates to 5
decimals, which keeps them stable between updates. Two items at the same position are rare;
when it happens, match by position + type first, then by position alone.

**Not logged:** resource fields and mines (they never change team), and items in the very
first update after opening the page or switching shards. That first update is the baseline;
without it the log would start with thousands of "built" entries.

## v1: in the browser (done)

### Store: `src/stores/warlog.js`

Following the `svelte` skill, all logic lives in a store; the component only renders.

- Subscribes to the world store. Keeps the previous items per hex, keyed by position.
- On each update, for every hex whose `v` changed, compares the items and creates entries:
  `{ id, time, kind, team, icon, text, place, hex, x, y }`. `time` is the hex's `l`
  (when the War API says it changed), not the time the browser noticed; `x`/`y` are map
  pixels, `place` is the nearest named place from `search.placeOf()`.
- Subscribes to the war store for the victory town totals and the winner.
- Newest first, at most 200 entries in memory; older ones drop off.
- Resets when the shard changes.
- Tracks the number of entries added since the panel was last opened, for a badge.

The comparison itself goes in a pure function, `src/lib/warlog-diff.js`:
`diffHex( previousItems, nextItems ) → changes[]`. It has no store or browser dependencies, so
it can be tested with Node's built-in test runner (`node --test`) without adding packages, and
v2 can port it to PHP one-to-one.

### Importance

Not every change matters equally. Each entry gets a level:

- **major:** victory towns captured, lost, or scorched; relic bases and keeps; rocket sites
  armed or fired (icons 70–72); victory town totals; the war ending.
- **normal:** other town bases, upgrades, structures built or destroyed.

The panel shows both by default, with a "Major updates only" toggle remembered in `localStorage`
(the same pattern as the settings store).

### Component: `src/components/warlog.svelte`

- **Placement:** left side, between the logo (top) and the war overview (bottom), about
  280 px wide, scrolling. Collapsible to a small "War log" button with a badge for unseen
  entries; collapsed by default on screens narrower than 760 px.
- **Entry:** team colour stripe on the left (the war overview's team colours), the icon, the
  text with the team in bold, the place and hex on a second line, and the time ("2 min ago",
  updated every minute; the full time in a `title`).
- **Click or Enter:** `view.focus( { x, y, scale: 1.5 } )`, the same as choosing a structure
  in the search, including the marker ring.
- **Empty state:** "Watching for changes. Captures, new structures and scorched towns appear
  here while this page is open."
- **Accessibility:** the list is a `<ul>` of buttons; new entries are announced through an
  `aria-live="polite"` region, limited to major entries so a screen reader is not flooded.
- **Styles:** `assets/css/warlog.css`, loaded from `app.html`, using the panel style from
  `panels.css`.

### Tests

- Unit (`node --test`): `diffHex` for capture, loss, upgrade, scorch, build, destroy, and
  "nothing changed".
- Browser (Playwright): route `/api/data/able` to return a fixed response, then a second one
  with one town captured; expect one log entry with the right text, and clicking it centres
  the map on that town. Using fixed responses keeps the test independent of the live war.

## v2: the server keeps the log

### Why

- **One source of truth.** Every visitor sees the same entries, with the same wording and
  times, instead of each browser building its own.
- **History.** The log is full when the page opens, and covers the hours nobody had it open.
- **Less work in the browser.** Comparing ~2,900 structures every 10 seconds moves to the
  server, which does it once for everyone.

### Recording on the server

Two triggers run the same recorder, `.api/lib/warlog-recorder.php`:

1. **Cron, the main one.** A DirectAdmin cron job runs `.api/cron/record.php` every minute, so
   the log keeps filling when nobody visits. DirectAdmin can run PHP scripts on a schedule
   without SSH (the earlier cron problem was git, not cron), for example:
   `/usr/local/bin/php /home/<user>/domains/fatt.fali.se/public_html/.api/cron/record.php`.
   The script sits in `.api/`, so the web server never serves it.
2. **Piggyback, for detail.** While visitors are on the page, `/api/data` is already fetched
   every few seconds. Whenever it fetches fresh data from the War API (its 3-second cache
   expired), it hands that data to the recorder too. That gives 10-second resolution while
   people watch, at no extra War API cost, and keeps the log working if the cron job is
   missing or broken.

The recorder, for each live shard:

- compares every hex whose `version` changed with the last snapshot, using a PHP port of
  `diffHex` (`.api/lib/warlog-diff.php`), and stores the changes as events;
- records victory town totals and the war's winner from `worldconquest/war` and the counts,
  the same as the v1 store does from the war store;
- saves the new snapshot;
- stores the time of the last successful run, so the API can say how fresh the log is.

The first run of a war (or after a reset) only saves a snapshot, the same baseline rule as v1.
Hexes are fetched with ETags (`If-None-Match`), so unchanged hexes answer 304 and cost almost
nothing. A non-blocking `flock` makes overlapping runs (cron and a request at the same moment)
skip instead of recording twice.

**Same results in PHP and JavaScript:** the unit test cases move into shared JSON fixtures
(`.app/src/tests/fixtures/warlog-diff.json`: previous items, next items, expected changes). The
Node tests and a small PHP test script both run them, so the two ports cannot drift apart.

### Storage

SQLite in `.api/data/warlog.sqlite` (needs `pdo_sqlite`; check DirectAdmin's PHP extensions).
One file, no database server, and hidden like the rest of `.api/`. If `pdo_sqlite` is not
available, an append-only JSON-lines file per shard and war works too, at the cost of slower
"since" queries.

```sql
CREATE TABLE events (
  id         INTEGER PRIMARY KEY,
  shard      TEXT    NOT NULL,
  war        INTEGER NOT NULL,
  time       INTEGER NOT NULL,   -- ms, from the hex's lastUpdated
  hex        TEXT    NOT NULL,
  kind       TEXT    NOT NULL,   -- captured, lost, upgraded, scorched, built, destroyed, construction, completed, victory, won
  major      INTEGER NOT NULL,   -- 1 or 0
  icon       INTEGER,
  icon_from  INTEGER,
  team       TEXT,
  team_from  TEXT,
  flags      INTEGER,
  flags_from INTEGER,
  x          REAL,               -- position in the hex, 0–1, as in the API
  y          REAL,
  value      INTEGER,            -- victory: towns held
  required   INTEGER             -- victory: towns needed
);
CREATE INDEX events_by_war ON events ( shard, war, id );

CREATE TABLE snapshots (
  shard TEXT, hex TEXT, version INTEGER, etag TEXT, items TEXT,  -- items as JSON
  PRIMARY KEY ( shard, hex )
);

CREATE TABLE status (
  shard TEXT PRIMARY KEY, war INTEGER, recorded_at INTEGER      -- last successful run, ms
);
```

Events store data, not sentences: the browser builds the text with the same `toEntry()` code
v1 uses, so wording can change without touching stored data. A war produces a few thousand
events, so no clean-up is needed for a long time; old wars can be archived or deleted per
`war`.

### API

- `GET /api/log/<shard>?limit=100` — the latest events of the current war, newest first.
- `GET /api/log/<shard>?since=<id>` — events after the newest one the browser has.
- `GET /api/log/<shard>?before=<id>&limit=100` — older events, for scrolling back.
- `&major=1` on the first request also returns the major events older than the latest ones
  (up to 200), so a victory town, relic or rocket from earlier in the war is not missed by a
  page opened later.

Every response includes `{ war, recordedAt, events }`. `recordedAt` is the last successful
recording; the browser uses it to judge whether the log is current. Parameters are validated
as integers, `limit` is capped at 200, and responses may be cached for a few seconds.

### Browser: server first, own comparison as fallback

The warlog store gets two sources and shows one at a time:

- **Server (normal):** on page load, fetch the latest 100 events; then, with every map update
  (every 10 seconds), fetch `?since=<newest id>`. Events become entries through the existing
  `toEntry()`.
- **Browser (fallback):** the v1 comparison keeps running in the background on the map data
  the page already has (it is cheap, and it means the fallback has a baseline the moment it is
  needed), but its entries are only shown while the server log is unhealthy.

The server log counts as **unhealthy** when the log request fails or times out (5 seconds),
returns an error, or its `recordedAt` is more than 3 minutes old while the map data itself is
fresh (the recorder has stopped). It counts as healthy again after one good response.

Switching:

- **To fallback:** keep the server entries already shown, add the browser's entries on top,
  and show a small notice in the panel: "Server log unavailable; showing changes seen by this
  browser."
- **Back to server:** fetch `?since=<last server id>`, replace the browser's entries with the
  server's (they describe the same changes, and the server's are complete), and hide the
  notice.

Entries carry their source (`server` or `browser`), so the two are never mixed into
duplicates.

### Tests

- PHP and Node unit tests on the shared fixtures.
- Recorder: run it twice on two saved War API responses and check the stored events.
- Browser (Playwright):
  - the log is filled on page load from a routed `/api/log` response;
  - new events from `?since=` appear;
  - when `/api/log` is routed to fail, the notice appears and a change in routed `/api/data`
    responses still shows up (fallback);
  - when `/api/log` answers again, the notice goes and the server entries replace the
    browser's.

### Later ideas this enables

- A timeline that replays the map at any moment of a war.
- History per region or town ("captured 6 times this war").
- Notifications for a chosen town or hex.
- Rocket launches drawn as arcs (`2026-10-07-rocket-arcs.md`), detected on the server where the
  full history is available.
